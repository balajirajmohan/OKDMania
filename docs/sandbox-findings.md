Pre-implementation validation for `infra/aws/sandbox/` (spec section 25).
Read this before you expect the two Fedora boxes to "become OKD".

Date: 2026-09-10 · Account: `853973692277` · Region: `us-east-1`

## 1. Plain Fedora + Ansible cannot produce an OKD 4.x cluster

**This is the important one.**

The spec's mental model is: launch Fedora VMs → Ansible installs OKD → master +
worker cluster. That is an **OKD 3.11** workflow (`openshift-ansible`), and OKD
3.11 is years past EOL (Kubernetes 1.11).

**OKD 4.x (what the team is evaluating — root README D007 = 4.21) works nothing
like that:**

| Requirement | OKD 4.x reality | This sandbox |
|---|---|---|
| Node OS | **Fedora CoreOS (FCOS)** / SCOS — immutable, no `dnf install` of cluster components | plain Fedora Cloud |
| Provisioning | **Ignition** configs generated by `openshift-install` | cloud-init |
| Installer | `openshift-install` (IPI or UPI) drives the whole thing | none |
| Bootstrap node | a **temporary** extra machine is mandatory during install | not present |
| API/MCS load balancer | LB for `:6443` and `:22623` (internal) | none |
| Ingress load balancer | LB for `*.apps` `:80/:443` | none |
| DNS | real, resolvable `api.`, `api-int.`, `*.apps.<cluster>.<base>` (Route 53) | none |
| Control-plane count | **3** (etcd quorum) | 1 |
| Ansible's role | at most bare-metal host prep; it does **not** install the cluster | — |

### Closest compatible alternatives

1. **Keep this sandbox as a learning/ops environment (chosen).** The Fedora
   boxes are scratch space; `okd-ansible` and `okd-runner` are the tooling and
   CI hosts. Use them to get fluent with `oc`, `openshift-install`,
   `butane`/Ignition, and Ansible while the **real** cluster is built via AWS
   UPI (root README **D031**). This sandbox's VPC/SG/key-pair/state modules are
   also a stepping stone toward the UPI Terraform.
2. **Single-Node OKD (SNO)** if you want a real cluster from these repos: needs
   an FCOS AMI + Ignition + a single node with **8 vCPU / 16–24 GB / 120 GB**
   (bigger than `m5.xlarge`), plus DNS and a minimal LB or `/etc/hosts`
   trickery. That is a different module set — out of scope here, tracked as a
   possible future `infra/aws/sno/`.
3. **Plain Kubernetes / k3s / kubeadm** on the existing Fedora boxes for
   muscle memory only — explicitly *not* OKD, so it doesn't serve the POC's
   evaluation goal.

**Decision:** option 1. `infra/aws/sandbox/` provisions infrastructure only and
does not claim to install OKD.

## 2. Fedora AMI discovery — `ec2:DescribeImages` is SCP-denied

```
$ aws ec2 describe-images --owners 125523088429 --filters Name=name,Values=Fedora-Cloud-Base-*
An error occurred (UnauthorizedOperation) ... with an explicit deny in a
service control policy: .../p-sn66yufq
```

So `data "aws_ami"` **fails at plan time** in this account. Consequences:

- **Fedora AMI** → plain `fedora_ami_id` variable (no default, validated).
  Master and worker share it so their Fedora versions match (spec section 5).
  Find the current ID at <https://fedoraproject.org/cloud/download> (per-region
  AMI table / "Launch" link), or via `aws ec2 describe-images` once the SCP is
  relaxed, or the EC2 console → AMIs → Public images → owner `125523088429`.
- **Ubuntu AMI** → the Canonical **SSM public parameter** still works
  (`ssm:GetParameter` is allowed):
  `/aws/service/canonical/ubuntu/server/24.04/stable/current/amd64/hvm/ebs-gp3/ami-id`
  → resolved `ami-025d99823a4caad37` on 2026-09-04. `data "aws_ssm_parameter"`
  is the primary path; `ubuntu_ami_id` overrides it.

If a dedicated AWS account without this SCP is used later, switch
`fedora_ami_id` to a `data "aws_ami"` lookup (owner `125523088429`,
`Fedora-Cloud-Base-*`, `architecture = x86_64`, newest `CreationDate`).

## 3. Terraform S3 backend locking — `use_lockfile`, not DynamoDB

- Local Terraform is **1.15.8** (`>= 1.11`).
- Since **1.11**, `dynamodb_table` on the S3 backend is **deprecated** (still
  works; slated for removal). The replacement is native **`use_lockfile =
  true`** — S3 conditional writes, no extra infrastructure.
- **Implemented:** `environments/sandbox/backend.tf` uses `use_lockfile = true`.
  `bootstrap/` still creates the `okd-terraform-lock` DynamoDB table (LockID,
  PAY_PER_REQUEST, PITR, deletion protection) so the legacy path stays
  available — uncomment one line in `backend.tf` to switch.

## 4. EC2 architecture compatibility — OK

- `m5.xlarge` and `t3.xlarge` are **x86_64**, 4 vCPU / 16 GiB each. Fedora Cloud
  and Ubuntu both publish x86_64 images. No Graviton/arm64 mismatch.
- `ec2:CreateVpc` and `ec2:RunInstances` **dry-runs succeed** in this account.
- `t3.*` is **burstable** — fine for `okd-ansible`, `okd-runner`, and a scratch
  worker; watch CPU credits under real load. A production control plane should
  not be burstable (`m5`/`m6i`).

## 5. Instance sizing vs OKD — adequate for a *sandbox* only

- Real OKD 4.x control-plane minimum is **4 vCPU / 16 GB** — `m5.xlarge` is
  *exactly* that, i.e. tight. The real cluster's sizing lives in the root
  README (**D011**: masters `m6i.xlarge`, workers `m6i.2xlarge`, 120 GB gp3),
  driven by the OpenTelemetry Demo + Kafka + Loki workload.
- One master = **no etcd quorum / no HA**. Fine for a scratch box, not a
  cluster.
- No bootstrap node is provisioned (see finding 1).

These are acceptable because the sandbox's job is learning and tooling, not
running the evaluation workload.

## 6. IAM — instance profile is optional

225 IAM roles already exist in the account; `iam:CreateRole` may be
SCP-restricted (not verified). The `iam-instance-profile` module is therefore
**off by default** (`create_instance_profile = false`). Enable it for AWS
Systems Manager **Session Manager** (shell access with port 22 closed); it
attaches only `AmazonSSMManagedInstanceCore`.

## How this sandbox feeds the UPI build

The modules here (`vpc`, `security-groups`, `key-pair`, `ec2`, S3+DynamoDB
`bootstrap`) are deliberately close to what the UPI stack needs. When Balaji
starts `infra/aws/upi/` (root README D031), the VPC layout, tagging convention,
remote-state backend, and key handling carry straight over; UPI adds the
bootstrap machine, NLBs (`:6443`, `:22623`, `:80/:443`), Route 53 records,
IAM instance profiles per role, and FCOS + Ignition. The `okd-ansible` and
`okd-runner` hosts remain useful throughout as the ops and CI boxes.
